### CCC 로그인 연동 — 받아오는 정보
- **필수**: `ccc_id`(고유·불변 식별자) · 이름 · 전화번호
- **받음**: 소속 지구(→ 간사 지구 자동배정) · 캠퍼스
- **확인 예정**: 간사/순장/순원 직분 (오면 권한 부여·표시 보조)

- **학생은 CCC 로그인 안 함** — 예약번호 + 전화 끝 4자리 유지 (비CCC 학생 포함 가능해야 하므로)

## 1. 한 줄 소개 + 현행 문제

### 한 줄
> 카톡 오픈채팅으로 처리하던 **타지구 차량 자리 나눔**을 시스템으로 — 공정하게, 투명하게, 편리하게.

### 현행 방식
1. 각 지구 차량 담당 간사가 본인 지구 배차 완료
2. 남는 자리를 전국 차량 간사 톡방에 공지
3. 다른 지구 간사들이 채팅으로 선착순 손들기
4. 매칭 후 1:1 톡으로 송금 정보 교환
5. 운행 당일 학생·간사 픽업 안내도 1:1 톡

### 비효율

| 문제 | 영향 |
|---|---|
| 채팅 순서가 곧 선착순 | 누가 먼저인지 분쟁 |
| 메시지 묻힘 | 자리 놓침 |
| 송금 확인 1:1 분산 | 중복·누락 |
| 명단 자투리 톡 확정 | 미탑승 사고 |
| 정산 사람 머릿속에만 | 회계 불투명 |
| 본인 지구 차 떠난 후 학생이 타지구 차 | 본인 지구 간사 관리 불가, 학생 혼자 |

## 2. 핵심 컨셉

### 자리 매칭 (간사 ↔ 간사)
- **신청 큐 시각순 정렬**: 신청 시각(FIFO) 기준 정렬해 보여줌 — **강제 잠금 없음**
- **간사 수동 승인**: 공급 간사가 큐를 보고 원하는 신청·학생을 직접 선택해 승인 (연락 두절 학생 등 행정 대응 자유도 확보)
- **부분 매칭 = 간사 수동 선택**: 자리 부족 시 공급 간사가 태울 학생을 직접 고름 (우선순위는 참고 힌트일 뿐 자동 아님)
- **송금 지연 = 소프트 리마인더**: 자동 만료 없음. "송금 지연" 표시·알림 후 간사가 수동으로 `[자리 풀기]`
- **매칭 후 공급 측 자의 취소 불가**: 학생 안심 (입금 확정(paid) 매칭)
- **학생 자의 취소 가능**: 양쪽 간사 자동 알림 + 환불 각 지구 문의

### 학생 진입 (간사 → 학생)
- **별도 가입 X**: 예약번호(`BUS-XXXX`) + 이름 + 전화 끝 4자리
- 카톡 링크로 바로 진입 → 본인 매칭 화면
- 출발지 카카오맵 임베드, 담당 간사 연락처, Trip 채팅, **자의 취소** 모두 가능

### 운영 (마스터)
- 간사 가입 승인·지구 부여
- 거절 발생·시스템 장애 알림
- 전국 정산 매트릭스
- 데이터 익명화 D-day 모니터링

## 3. 사용자 권한 모델 (3종)

### 👤 마스터 (Master) — CCC IT 사역부
- **인증**: 마스터 비밀번호만 (외부 OAuth X)
- **권한**:
  - 시스템 전체 관리
  - 간사 가입 승인·권한 해제
  - 신청 마감일·점검 모드 settings
  - 전국 정산 매트릭스
  - 거절 발생 모니터링
  - 출발지 미지정 위험 Trip (사실상 발생 X — §10 참조)
- **계정 수**: 초기 1명 (CCC IT 사역부 운영팀), V2에서 부서 내 위임 가능

### 🧑‍✈️ 차량 간사 (Operator)
- **인증**: **CCC 로그인** (ccc-summer 진입점에서 CCC가 신원 전달 → 우리가 검증 → 자체 세션 발급) + 마스터 승인 대기 → 승인 후 활성
- **가입 시 등록 (필수)**:
  - 본인 정보 (CCC에서 이름·전화·소속 지구 수신 — 지구가 오면 자가선택 생략)
  - 본인 지구 확인 (CCC 미제공 시 52개 중 선택)
  - **상행 출발지 N개** (지구 내에서 어디서 출발하는지)
  - **하행 출발지 N개** (평창에서 어디서 출발하는지)
  - **하행 도착지 N개** (지구 내 어디로 도착하는지)
- **권한**:
  - Trip CRUD (등록·수정·삭제, location은 본인이 등록한 것에서 선택)
  - Offer 공개 (남는 자리)
  - 다른 지구 Trip 검색·신청 (학생 명단 + 우선순위)
  - 매칭 큐 승인·거절 (시각순 정렬, 자유 선택)
  - 송금 완료 알림 / 입금 확인 / Phase 2 취소
  - 본인 지구 정산 조회
- **계정 수**: 지구마다 1~2명 (전국 50+명)

### 🧑‍🎓 학생 (Passenger)
- **인증**: 별도 가입 X — 예약번호 + 이름 + 전화 끝 4자리
- **권한**:
  - 본인 매칭 조회 (여러 매칭 다중 카드)
  - 출발지 지도·시간·간사 연락처
  - Trip 채팅 (paid 이후)
  - 자의적 매칭 취소
- **계정 수**: 수련회당 수백~수천

## 4. 운영 흐름 (단계별, 전체 그림)

```
[수련회 D-약 2~3개월]
  → 마스터: 시스템 활성, 신청 마감일 settings
  → 간사: CCC 로그인 → 가입 → (지구 자동 수신/확인) + location 등록
  → 마스터 승인 → 간사 활성

[수련회 D-약 1~2개월: 본인 지구 배차]
  → 간사가 본인 지구 학생 받기 (시스템 외 또는 별도 채널)
  → 본인 차량 정원·요금 정해짐

[수련회 D-약 4주~1주: 타지구 매칭 활성 단계]
  → 공급 지구 간사: 본인 차량 등록 → 남는 자리 공개 (Offer)
  → 수요 지구 간사: 다른 지구 Trip 검색 → 학생 명단(우선순위는 힌트) → 신청
  → 큐 시각순 정렬 (표시만, 잠금 없음)
  → 공급 지구: 큐에서 원하는 신청·학생을 수동 승인 (자유 선택)
  → 매칭 확정 → 송금 단계 (자동 만료 없음)

[송금 단계]
  → 수요 지구: 송금 + "송금 완료" 클릭
  → 공급 지구: 통장 확인 + "입금 확인" 클릭
  → 예약번호 발급
  → 수요 지구: 학생들에게 카톡 공유

[수련회 D-1주~당일]
  → 학생: 예약번호로 접속 → 본인 매칭 확인
  → Trip 채팅 활성
  → 출발 D-1, D-1h 알림
  → 운행

[수련회 종료 후]
  → 정산 (캠퍼스 자율, 시스템은 ledger 표만)
  → 사후 환불 (각 지구 사적 합의)

[수련회 종료 + 90일]
  → 매일 새벽 3시 KST 자동 익명화
```

## 5. 핵심 시나리오 9개

### S1. Trip 등록 + 자리 공개 (공급 지구)

```
1. 간사 A 로그인 (CCC 로그인, 이미 마스터 승인 완료)
2. /operator/trips/new
3. Trip 정보 입력:
   - 방향: 하행
   - 출발지: A가 가입 시 등록한 하행 출발지 중 선택 (예: "평창 봉평면 ○○로")
   - 도착지: A가 가입 시 등록한 하행 도착지 중 선택 (예: "광주 충장로 1가")
   - 출발 시각: 2026-07-30 14:00
   - 정원: 44석
   - 좌석당 요금: 35,000원
   - 메모: 500자 이내
4. 저장 → status=draft
5. 본인 지구 학생 배차 후 남는 자리 10개 → "타지구 공개" 토글 ON
6. SeatOffer 생성 → status=published
7. 전국 다른 간사들의 검색 결과에 노출
```

### S2. 신청 (수요 지구)

```
1. 간사 B 로그인 → /operator/requests/new
2. 검색: 평창→부산, 2026-07-30
3. Trip 카드 선택
4. 학생 명단 입력 (5명):
   - 1️⃣ 김○○ (우선순위 1) · 010-XXXX-1234 · 부산대
   - 2️⃣ 박○○ (우선순위 2) · 010-XXXX-5678 · 부경대
   - 3️⃣ 이○○ (우선순위 3)
   - 4️⃣ 최○○ (우선순위 4)
   - 5️⃣ 정○○ (우선순위 5)
   ※ 우선순위 = 공급 간사에게 주는 참고 힌트 (입력 순서 default, 수정 가능). 자동 매칭 아님
5. 개인정보 동의 confirm 체크박스 필수
6. [신청] → SeatRequest 생성 (requested_at=NOW, status=queued)
7. A에게 알림 (인앱 + PWA 푸시)
```

### S3. 매칭 승인 (간사 수동 선택)

```
[자유 선택 — FIFO 강제 잠금 없음]
- 큐는 신청 시각순으로 정렬해 보여주기만 함 (공정성 참고용)
- 공급 간사가 어느 신청이든, 그 안의 어느 학생이든 직접 골라 승인 가능
- 연락 두절·긴급 등은 간사 재량으로 순서와 무관하게 처리

1. A가 /operator/trips/:id 진입 → 큐(시각순) 확인
2. 승인할 신청 선택 + 태울 학생 선택 (자리보다 많으면 일부만 선택)
3. [승인] 클릭 → 안내 모달:
   ⚠️ "입금 확정(paid) 후에는 공급 지구 본인 사정으로 매칭 취소가 불가능합니다.
       학생 자의 취소 또는 송금 미완료 시에만 자리가 풀립니다.
       신중히 진행해 주세요."
4. [승인 확정]:
   → 선택한 학생들만 매칭 생성 (학생 1명당 Match 1개)
   → 매칭 안 된 학생은 큐에 그대로 잔류 (간사가 나중에 다시 선택)
   → 자동 분할·자동 거절 없음 (전부 간사 판단)
5. B에 알림: "매칭 확정 — 송금 후 [송금 완료] 눌러주세요" (마감 시한 없음, 지연 시 리마인더)

[거절 케이스]
- [거절] 클릭 → 사유 입력 (10자 이상 필수)
- B 알림 + 마스터 알림 (단순 로그, 임계값 없음)
```

### S3b. 잔여 자리 변동 시 (수동 재매칭)

```
Trigger: 송금 지연 [자리 풀기], Phase 2 취소, 학생 자의 취소 → 잔여 자리 +N

→ 시스템: 자동 재매칭 안 함. 대신
   - 큐에 남아있던 신청들을 그대로 다시 노출 (시각순 정렬 유지)
   - 공급 간사에게 "자리 N석 생김" 알림
   - 거절·취소됐던 신청 지구에 "자리 났어요" 재신청 추천 알림

→ 공급 간사가 큐에서 다시 원하는 학생을 수동 승인 (S3와 동일)
```

### S4. 송금 + 입금 확인 + 만료

## 7. 매칭 방식 (시각순 정렬 + 간사 수동 선택)

### 원칙
- 신청 시각(requested_at) = 큐 **정렬 키** (공정성 참고용으로 보여주기만)
- **강제 잠금 없음** — 공급 간사가 큐 어느 항목이든 승인/거절 가능
- 부분 매칭 = **간사 수동 선택** (태울 학생을 직접 고름, 우선순위는 힌트)
- 자동 분할·자동 후속 매칭·자동 거절·자동 만료 **모두 없음**

### 흐름

```
1. 큐 표시: 해당 Trip의 queued 신청을 requested_at 오름차순 정렬
2. 공급 간사가 신청 1건 선택 → 그 안에서 태울 학생 선택 (자리 ≥ 선택 인원)
3. [승인] → 선택 학생만 Match 생성. 나머지는 큐 잔류
4. 자리 부족·연락 두절 등은 간사가 순서와 무관하게 재량 처리
5. 자리가 다시 나면(취소·자리 풀기) 큐를 다시 노출 + 알림 → 간사가 다시 수동 선택
```

### 왜 강제(FIFO 잠금)를 풀었나
- v1.0은 "친한 지구 선별 차단" 위해 큐 1번째만 강제했으나,
  학생 연락 두절 등 **행정상 빠른 대응**이 막히는 부작용 → 간사 피드백 반영해 자유도 부여.
- 강제를 푼 대신 **"누가 언제 어느 신청을 승인/거절했는지" 로그**로 사후 투명성 확보.

## 8. 케이스별 처리

### A. 부분 매칭
- 자리 부족 시 공급 간사가 태울 학생을 **수동 선택** (우선순위는 힌트)
- 매칭 안 된 학생은 큐에 그대로 잔류 (자동 분할·priority 재정렬 없음)
- 잔여 자리 풀리면 큐 재노출 + 알림 → 간사가 다시 수동 선택 (S3b)

### B. 송금 지연 (송금 미보고, 자동 만료 없음)
- 매칭 후 일정 시간 경과 + payment_reported = NULL → "송금 지연" 리마인더만
- 자리 회수는 공급 간사가 [자리 풀기] 눌러 수동으로 → S3b + 재신청 추천 알림

### C. Phase 2 취소 (송금 보고 후 미입금)
- 공급 지구가 [매칭 취소] 사유 필수 → cancelled
- 자리 풀림

### D. 매칭 paid 후 공급 측 자의 취소
- **불가능** (학생 안심)
- 학생 자의 취소 또는 시스템 외 협의로만

### E. 학생 자의 취소
- /me/cancel/:matchId → 양쪽 간사 알림 + 자리 풀림
- 환불 = 각 지구로 문의 (시스템 외)
- D-1 이내 = 강한 안내문구 ("환불 어려울 수 있음")

### F. 간사 거절
- 큐에서 신청 선택 → [거절] + 사유 10자+ 필수
- 신청 지구 + 마스터 알림 (V1 단순, 임계값 X)

### G. 자리 다시 풀림 (S3b)
- 자동 재매칭 없음 — 큐 재노출 + 공급 간사 알림
- 거절·취소된 신청 지구에 "자리 났어요" 재신청 추천 알림
- 자리 풀릴 때마다 (스팸 우려 시 V1.5에서 묶음 처리 검토)

### H. Trip 정보 변경
- 매칭 발생 전: 자유 수정 + 삭제 가능
- 매칭 발생 후:
  - 정원 ↑ OK / 정원 ↓ 매칭된 좌석 이상만
  - 요금·시간·location 변경 = 자동 알림 (양쪽 + 학생)
  - 방향 = 변경 X
- 출발 D-1 이후: 변경 가능하지만 강한 안내문구

### I. 간사 권한 해제
- 마스터 /admin/operators → [비활성화] + 사유
- 즉시 권한 회수·세션 종료
- 해당 간사 + 같은 지구 다른 간사 알림 (인수인계)

## 13. PWA 푸시 알림

### 지원 환경
| OS | 가능 조건 |
|---|---|
| Android (모든) | "홈 화면 추가" 없이도 푸시 가능 |
| iOS 16.4+ | "홈 화면 추가" 필수 (Safari에서) |
| iOS 16.4 미만 | 푸시 불가 (인앱 알림만) |

### 학생 진입 — 옵션 C (마찰 최소)
- 링크 → **바로 웹 진입** (홈화면 추가 강제 X)
- "홈 화면 추가" 안내 = 부드러운 배너 (선택)
- 첫 매칭 paid 시점에 "푸시 받으시겠어요?" 자연스럽게 권유

### 카톡 내장 브라우저 대응
- 카톡 내장 브라우저는 "홈 화면 추가" 불가
- "Safari로 열기" 안내 표시

### 간사 푸시도 동일 (CCC 전용 앱 없음)
- 간사도 카톡/크롬/사파리로 접근 (전용 앱 없음 — ccc-summer 사이트가 진입점)
- 카톡 내장 브라우저면 푸시 불가 → 크롬·사파리 + 홈 화면 추가 시 푸시
- 따라서 간사 알림도 **"인앱 항상 + 푸시 옵트인"** (기존 '간사 푸시 당연' 가정 수정)

### iOS QA 강화
- 출시 전 실기기 검증 필수
- Playwright + 실기기 체크리스트

## 14. 마스터 운영

### 인증
- `/admin/login` → 마스터 비밀번호만 (외부 OAuth X)
- 24h 세션, 5회 실패 1h 잠금
- 16자+ · 1Password · 90일 rotation

- 오늘 알림 (거절·장애 등)

### 간사 가입 승인 (`/admin/operators/pending`)
- 가입 신청자 목록 (이름·전화·지원 지구·신청일)
- [승인] [거절] 액션

### 간사 권한 해제 (`/admin/operators`)
- 활성 간사 목록
- [비활성화] → 권한 즉시 회수 + 세션 종료 + 알림

### 거절 모니터링 (`/admin/rejections`)
- 거절 발생 단순 목록 (V1)
- 시각·공급·신청·인원·사유
- V2: 임계값·통계 분석

### 정산 매트릭스 (`/admin/settlement`)
- 전국 N×N 매트릭스
- 셀 클릭 → 해당 ledger
- CSV 내보내기

### 시스템 settings (`/admin/system`)
- 전국 신청 마감일
- 점검 모드 (시스템 일시 잠금)
- 로그 조회

## 17. FAQ

**Q1. 차량 간사가 아니어도 시스템을 쓰나요?**
간사만 로그인. 학생은 카톡 받은 예약번호로 본인 매칭만 조회.

**Q2. 송금은 시스템에서 처리하나요?**
송금 자체는 기존처럼 지구 간 직접 계좌이체. 시스템은 송금 완료·입금 확인을 추적하고 정산 ledger를 자동 생성.

**Q3. 송금이 늦어지면요?**
자동 만료는 없습니다. "송금 지연" 리마인더가 가고, 공급 간사가 판단해 [자리 풀기]를 누르면 그때 자리가 풀립니다. 풀리면 거절·취소됐던 신청 지구에 "자리 났어요" 재신청 알림.

**Q4. 매칭 후 취소는 가능한가요?**
- 공급 지구 자의 취소 = **불가능** (학생 안심 보장)
- 학생 자의 취소 = 가능 (양쪽 간사 자동 알림)
- 송금 보고했지만 실제 입금 없는 경우 = 공급 지구 [매칭 취소] 가능

**Q5. 학생 정보는 누가 보나요?**
매칭 양측 지구 차량 간사만. 외부에는 비공개.

**Q6. 핸드폰 알림은 어떻게 받나요?**
"홈 화면 추가" 시 PWA 푸시 알림. iOS 16.4+ + Safari로 추가 / Android 거의 모두. 안 해도 인앱 알림은 그대로.

**Q7. 환불은 어떻게 받나요?**
시스템에서 자동 정산 X. **각 지구 차량 간사에게 직접 문의**.

**Q8. 출발 장소가 바뀌면 알 수 있나요?**
변경 시 매칭된 학생·신청 지구 간사 전원에게 자동 알림 (인앱 + 푸시 + 채팅).

**Q9. 카카오톡 알림톡으로 받을 수 있나요?**
V1.0에서는 사업자 등록 어려워 인앱·푸시만. V2에서 검토.

**Q10. 데이터는 얼마나 보관되나요?**
수련회 종료 후 90일 보관 → 매일 새벽 3시 자동 익명화. 정산 데이터는 회계 의무 5년 보관 (개인 식별 부분 마스킹).

**Q11. 우선순위는 어떻게 정하나요?**
수요 간사가 학생 명단 입력 시 자유롭게 부여 (1·2·3·...). 입력 순서 default, 수정 가능. **공급 간사가 누구를 태울지 고를 때 참고하는 힌트**일 뿐, 자동 매칭에 쓰이지 않습니다.

**Q12. 학생 한 명이 여러 매칭 가능한가요?**
가능. 상행+하행 = 2매칭. /me에 다중 카드.

**Q13. 한 지구에 출발지가 여러 개면?**
간사 가입 시 출발지·도착지를 N개 등록. Trip 등록 시 그 중 선택. 예: 서울처럼 큰 지구도 OK.

**Q14. 부분 매칭은 어떻게 동작하나요?**
자리가 부족하면 공급 간사가 태울 학생을 **직접 골라** 매칭합니다(자동 아님). 매칭 안 된 학생은 큐에 그대로 남고, 자리가 다시 나면 간사가 다시 선택합니다.

**Q15. 신청 순서대로 강제 승인하나요?**
아니요. 신청 시각순으로 **정렬해 보여주기만** 하고, 공급 간사가 자유롭게 선택합니다. 강제하면 연락 두절 학생 등 행정 대응이 막혀서, 자유도를 주되 승인·거절 내역을 로그로 남겨 투명성을 확보합니다.
