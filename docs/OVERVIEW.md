## 1. 한 줄 소개 + 현행 문제

### 한 줄
> 카톡 오픈채팅으로 처리하던 **타지구 차량 자리 나눔**을 시스템으로 — 공정하게, 투명하게, 편리하게.

### 현행 방식
1. 각 지구 차량 담당 간사가 본인 지구 배차 완료
2. 남는 자리를 전국 차량 간사 톡방에 공지
3. 다른 지구 간사들이 채팅으로 선착순 손들기
4. 매칭 후 1:1 톡으로 송금 정보 교환
5. 운행 당일 학생·간사 픽업 안내도 1:1 톡

### 비효율

| 문제 | 영향 |
|---|---|
| 채팅 순서가 곧 선착순 | 누가 먼저인지 분쟁 |
| 메시지 묻힘 | 자리 놓침 |
| 송금 확인 1:1 분산 | 중복·누락 |
| 명단 자투리 톡 확정 | 미탑승 사고 |
| 정산 사람 머릿속에만 | 회계 불투명 |
| 본인 지구 차 떠난 후 학생이 타지구 차 | 본인 지구 간사 관리 불가, 학생 혼자 |

## 2. 핵심 컨셉

### 자리 매칭 (간사 ↔ 간사)
- **신청 슬라이스 FIFO 큐**: 신청 시각 기준 자동 정렬
- **공급 지구 1번째만 승인 가능**: 친한 지구 선별 차단
- **우선순위 기반 자동 부분 매칭**: 자리 부족 시 간사가 등록한 우선순위대로 자동
- **24시간 송금 데드라인**: 매칭 후 안 누르면 자동 만료
- **매칭 후 공급 측 자의 취소 불가**: 학생 안심
- **학생 자의 취소 가능**: 양쪽 간사 자동 알림 + 환불 각 지구 문의

### 학생 진입 (간사 → 학생)
- **별도 가입 X**: 예약번호(`BUS-XXXX`) + 이름 + 전화 끝 4자리
- 카톡 링크로 바로 진입 → 본인 매칭 화면
- 출발지 카카오맵 임베드, 담당 간사 연락처, Trip 채팅, **자의 취소** 모두 가능

### 운영 (마스터)
- 간사 가입 승인·지구 부여
- 거절 발생·시스템 장애 알림
- 전국 정산 매트릭스
- 데이터 익명화 D-day 모니터링

## 3. 사용자 권한 모델 (3종)

### 👤 마스터 (Master) — CCC IT 사역부
- **인증**: 마스터 비밀번호만 (외부 OAuth X)
- **권한**:
  - 시스템 전체 관리
  - 간사 가입 승인·권한 해제
  - 신청 마감일·점검 모드 settings
  - 전국 정산 매트릭스
  - 거절 발생 모니터링
  - 출발지 미지정 위험 Trip (사실상 발생 X — §10 참조)
- **계정 수**: 초기 1명 (CCC IT 사역부 운영팀), V2에서 부서 내 위임 가능

### 🧑‍✈️ 차량 간사 (Operator)
- **인증**: Google OAuth + 마스터 승인 대기 → 승인 후 활성
- **가입 시 등록 (필수)**:
  - 본인 정보 (이름·전화)
  - 본인 지구 선택 (52개 중)
  - **상행 출발지 N개** (지구 내에서 어디서 출발하는지)
  - **하행 출발지 N개** (평창에서 어디서 출발하는지)
  - **하행 도착지 N개** (지구 내 어디로 도착하는지)
- **권한**:
  - Trip CRUD (등록·수정·삭제, location은 본인이 등록한 것에서 선택)
  - Offer 공개 (남는 자리)
  - 다른 지구 Trip 검색·신청 (학생 명단 + 우선순위)
  - 매칭 큐 1번째 승인·거절
  - 송금 완료 알림 / 입금 확인 / Phase 2 취소
  - 본인 지구 정산 조회
- **계정 수**: 지구마다 1~2명 (전국 50+명)

### 🧑‍🎓 학생 (Passenger)
- **인증**: 별도 가입 X — 예약번호 + 이름 + 전화 끝 4자리
- **권한**:
  - 본인 매칭 조회 (여러 매칭 다중 카드)
  - 출발지 지도·시간·간사 연락처
  - Trip 채팅 (paid 이후)
  - 자의적 매칭 취소
- **계정 수**: 수련회당 수백~수천

## 4. 운영 흐름 (단계별, 전체 그림)

```
[수련회 D-약 2~3개월]
  → 마스터: 시스템 활성, 신청 마감일 settings
  → 간사: Google 로그인 → 가입 → 본인 지구 + location 등록
  → 마스터 승인 → 간사 활성

[수련회 D-약 1~2개월: 본인 지구 배차]
  → 간사가 본인 지구 학생 받기 (시스템 외 또는 별도 채널)
  → 본인 차량 정원·요금 정해짐

[수련회 D-약 4주~1주: 타지구 매칭 활성 단계]
  → 공급 지구 간사: 본인 차량 등록 → 남는 자리 공개 (Offer)
  → 수요 지구 간사: 다른 지구 Trip 검색 → 학생 명단 + 우선순위 → 신청
  → 큐 FIFO 정렬
  → 공급 지구: 큐 1번째 승인 (또는 거절·부분 매칭 자동)
  → 매칭 확정 → 24h Phase 1 시작

[송금 단계]
  → 수요 지구: 송금 + "송금 완료" 클릭
  → 공급 지구: 통장 확인 + "입금 확인" 클릭
  → 예약번호 발급
  → 수요 지구: 학생들에게 카톡 공유

[수련회 D-1주~당일]
  → 학생: 예약번호로 접속 → 본인 매칭 확인
  → Trip 채팅 활성
  → 출발 D-1, D-1h 알림
  → 운행

[수련회 종료 후]
  → 정산 (캠퍼스 자율, 시스템은 ledger 표만)
  → 사후 환불 (각 지구 사적 합의)

[수련회 종료 + 90일]
  → 매일 새벽 3시 KST 자동 익명화
```

## 5. 핵심 시나리오 9개

### S1. Trip 등록 + 자리 공개 (공급 지구)

```
1. 간사 A 로그인 (Google OAuth, 이미 마스터 승인 완료)
2. /operator/trips/new
3. Trip 정보 입력:
   - 방향: 하행
   - 출발지: A가 가입 시 등록한 하행 출발지 중 선택 (예: "평창 봉평면 ○○로")
   - 도착지: A가 가입 시 등록한 하행 도착지 중 선택 (예: "광주 충장로 1가")
   - 출발 시각: 2026-07-30 14:00
   - 정원: 44석
   - 좌석당 요금: 35,000원
   - 메모: 500자 이내
4. 저장 → status=draft
5. 본인 지구 학생 배차 후 남는 자리 10개 → "타지구 공개" 토글 ON
6. SeatOffer 생성 → status=published
7. 전국 다른 간사들의 검색 결과에 노출
```

### S2. 신청 (수요 지구)

```
1. 간사 B 로그인 → /operator/requests/new
2. 검색: 평창→부산, 2026-07-30
3. Trip 카드 선택
4. 학생 명단 입력 (5명):
   - 1️⃣ 김○○ (우선순위 1) · 010-XXXX-1234 · 부산대
   - 2️⃣ 박○○ (우선순위 2) · 010-XXXX-5678 · 부경대
   - 3️⃣ 이○○ (우선순위 3)
   - 4️⃣ 최○○ (우선순위 4)
   - 5️⃣ 정○○ (우선순위 5)
   ※ 우선순위는 입력 순서 default, 명시 수정 가능
5. 개인정보 동의 confirm 체크박스 필수
6. [신청] → SeatRequest 생성 (requested_at=NOW, status=queued)
7. A에게 알림 (인앱 + PWA 푸시)
```

### S3. 매칭 승인 (FIFO + 우선순위 자동 부분 매칭)

```
[FIFO 강제]
- 큐 1번째에만 [승인]·[거절] 활성. 2번째 이하는 🔒 "1번 처리 후"

1. A가 /operator/trips/:id 진입 → 큐 1번째 (부산 5명) 확인
2. [승인] 클릭 → 안내 모달:
   ⚠️ "승인 후 공급 지구 본인 사정으로 매칭 취소가 불가능합니다.
       학생 자의 취소 또는 송금 미완료 시에만 자리가 풀립니다.
       신중히 진행해 주세요."
3. [승인 확정]:

   [케이스 A: 잔여 ≥ 5]
   → 5명 전체 자동 매칭 (학생 1명당 Match 1개, 각 24h Phase 1)

   [케이스 B: 잔여 = 3]
   → 우선순위 1·2·3 자동 매칭
   → 4·5는 새 SeatRequest로 큐 잔류 (parent_request_id, requested_at 원본, priority 1·2 재정렬)

   [케이스 C: 잔여 = 0]
   → 자동 거절 + 마스터 알림

4. B에 알림: "매칭 확정, 24h 내 송금 완료 클릭"
5. 큐 다음 항목이 1번째로

[거절 케이스]
- [거절] 클릭 → 사유 입력 (10자 이상 필수)
- B 알림 + 마스터 알림 (단순 로그, 임계값 없음)
```

### S3b. 잔여 자리 변동 시 자동 매칭

```
Trigger: Phase 1 만료, Phase 2 취소, 학생 자의 취소 → 잔여 자리 +N

→ 시스템 자동 처리:
   - 큐 잔류 SeatRequest 순회 (requested_at ASC)
   - 각 row의 unmatched 학생 ORDER BY priority ASC
   - 가능한 만큼 자동 매칭
   - 매칭된 학생들·간사들에 알림
   - 간사 개입 X (자동)

→ 거절·만료된 SeatRequest의 신청 지구에 "자리 났어요" 재신청 알림 (자리 풀릴 때마다)
```

### S4. 송금 + 입금 확인 + 만료

```
[Happy Path]
1. B 매칭 화면 → 송금 정보 (광주지구 계좌, 175,000 = 5 × 35,000)
2. B 실제 송금 실행 (시스템 외)
3. B "송금 완료" 클릭 → Match.status = payment_reported, payment_reported_at = NOW
4. A에 알림: "부산지구 송금 완료 보고"
5. A 통장 확인 → [입금 확인] → Match.status = paid, paid_at = NOW
6. 시스템: 학생 1명당 예약번호 발급 (예: BUS-7K9M)
7. B 화면에 학생별 카톡 공유 문구 + [복사] 버튼:
   ```
   [수련회 차량] 평창→부산 7/30(수) 14:00 출발
   김○○님 예약번호: BUS-7K9M
   링크: https://bus-cignal.vercel.app/r/BUS-7K9M
   본인 이름 + 전화 끝 4자리로 접속
   ```

[Sad Path 1 — Phase 1 만료]
- matched_at + 23h: B에 "1h 후 만료" 알림
- matched_at + 24h, payment_reported_at = NULL → 시스템 자동 expire (cron 1분 간격)
- Match.status = expired, 자리 풀림 → S3b 자동 매칭 trigger
- 거절·만료된 신청 지구에 K2 재신청 추천 알림

[Sad Path 2 — Phase 2 취소]
- B 송금 완료 클릭했지만 실제 입금 없음
- A 통장 확인 → 입금 없음 → [매칭 취소] (status=payment_reported에서만 활성, 사유 필수)
- Match.status = cancelled, 자리 풀림

[★ 매칭 후 공급 측 자의 취소 = 불가능]
- status=paid 매칭은 공급 지구가 임의 취소 X
- 학생 자의 취소 또는 시스템 외 협의로만 자리 회수
```

## 7. 매칭 알고리즘 (FIFO + 우선순위 기반 자동 부분 매칭)

### Fairness 원칙
- 신청 시각(requested_at) = FIFO 큐 정렬 키
- 큐 1번째만 승인 가능 (UI + 서버 강제)
- 부분 매칭 = 자동 처리 (우선순위 기반, 간사 추가 작업 X)

### 알고리즘 의사 코드

```python
def approve(request):
    assert request == queue(request.trip)[0]   # 큐 1번째 강제
    avail = available(request.trip)
    passengers = request.passengers.order_by('priority')
    
    if avail >= request.seat_count:
        # 전체 매칭
        for p in passengers:
            Match.create(trip, request, p, payment_due_at=NOW+24h)
        request.status = 'matched'
    elif avail > 0:
        # 우선순위 N명 매칭 + 잔여 큐 잔류
        for p in passengers[:avail]:
            Match.create(trip, request, p, ...)
        new_request = SeatRequest.create(
            parent_request_id=request.id,
            requested_at=request.requested_at,   # 원본 시각 유지
            status='queued'
        )
        # 새 row priority 1·2·... 재정렬
        for i, p in enumerate(passengers[avail:], start=1):
            p.move_to(new_request, priority=i)
        request.status = 'matched'
    else:
        # 잔여 0: 자동 거절 + 마스터 알림
        request.status = 'rejected'
        notify_master(request, 'risk_event')
```

### Fairness 사례

```
시각 t=1: B 5명 신청 (priority 1·2·3·4·5)
시각 t=2: C 4명 신청 (priority 1·2·3·4)
시각 t=3: B 추가 3명 신청 (별도 SeatRequest, priority 1·2·3)

A가 7자리 공급:
- 큐 1번 B(5) → 잔여 7 ≥ 5 → 전체 매칭. 잔여 2
- 큐 1번 C(4) → 잔여 2 < 4 → 부분 매칭. C 우선순위 1·2 매칭. 잔여 0.
  C의 우선순위 3·4는 새 row로 큐 잔류 (requested_at=t=2, priority 1·2 재정렬)
- 큐 1번 = C 잔류 (t=2). 다음 = B 추가(t=3)

→ ✅ "B 우선 · C 다음 · B 추가 후순위" 충족
```

## 8. 케이스별 처리

### A. 부분 매칭
- 자리 부족 시 우선순위로 자동 매칭

- 잔여 자리 풀리면 자동 후속 매칭 (S3b)

- 자리 풀림

- **불가능** (학생 안심)

- 큐 1번 [거절] + 사유 10자+ 필수

- 한국 PIPA (개인정보 보호법) 의무
- 수집 목적 (차량 매칭) 달성 후 지체 없이 파기·익명화

### 보관 기간
- 수련회 종료 + **90일** 보관 (사후 정산·문의 대응 기간)

- 익명화 = 이름 "○○○", 전화·이메일 해시화

- 회계 의무 5년 (개인 식별 마스킹)

익명화 D-day 카운트다운 상시 표시

### 안 하면?
- PIPA 위반 (과태료 최대 3,000만원)

## 17. FAQ

**Q1. 차량 간사가 아니어도 시스템을 쓰나요?**
간사만 로그인. 학생은 카톡 받은 예약번호로 본인 매칭만 조회.

**Q2. 송금은 시스템에서 처리하나요?**
송금 자체는 기존처럼 지구 간 직접 계좌이체. 시스템은 송금 완료·입금 확인을 추적하고 정산 ledger를 자동 생성.

**Q3. 24시간 안에 송금 못 하면요?**
매칭 자동 만료, 자리 다시 풀림. 큐 다음 지구로 진행. 거절·만료된 신청 지구에는 "자리 났어요" 재신청 알림.

**Q4. 매칭 후 취소는 가능한가요?**
- 공급 지구 자의 취소 = **불가능** (학생 안심 보장)
- 학생 자의 취소 = 가능 (양쪽 간사 자동 알림)
- 송금 보고했지만 실제 입금 없는 경우 = 공급 지구 [매칭 취소] 가능

**Q5. 학생 정보는 누가 보나요?**
매칭 양측 지구 차량 간사만. 외부에는 비공개.

**Q6. 핸드폰 알림은 어떻게 받나요?**
"홈 화면 추가" 시 PWA 푸시 알림. iOS 16.4+ + Safari로 추가 / Android 거의 모두. 안 해도 인앱 알림은 그대로.

**Q7. 환불은 어떻게 받나요?**
시스템에서 자동 정산 X. **각 지구 차량 간사에게 직접 문의**.

**Q8. 출발 장소가 바뀌면 알 수 있나요?**
변경 시 매칭된 학생·신청 지구 간사 전원에게 자동 알림 (인앱 + 푸시 + 채팅).

**Q9. 카카오톡 알림톡으로 받을 수 있나요?**
V1.0에서는 사업자 등록 어려워 인앱·푸시만. V2에서 검토.

**Q10. 데이터는 얼마나 보관되나요?**
수련회 종료 후 90일 보관 → 매일 새벽 3시 자동 익명화. 정산 데이터는 회계 의무 5년 보관 (개인 식별 부분 마스킹).

**Q11. 우선순위는 어떻게 정하나요?**
간사가 학생 명단 입력 시 자유롭게 부여 (1·2·3·...). 입력 순서 default, 명시 수정 가능. 잔여 자리 부족 시 우선순위 1번부터 매칭.

**Q12. 학생 한 명이 여러 매칭 가능한가요?**
가능. 상행+하행 = 2매칭. /me에 다중 카드.

**Q13. 한 지구에 출발지가 여러 개면?**
간사 가입 시 출발지·도착지를 N개 등록. Trip 등록 시 그 중 선택. 예: 서울처럼 큰 지구도 OK.

**Q14. 부분 매칭은 어떻게 동작하나요?**
간사가 신청 시 학생별 우선순위 부여. 잔여 자리 부족 시 우선순위 순으로 자동 매칭. 나머지는 큐 잔류 (자리 풀리면 자동 후속 매칭). **B 응답 기다리는 시간 없음.**

**Q15. 매칭 큐 1번째만 승인 가능한 이유?**
친한 지구 선별 차단. 누가 먼저 신청했는지 시스템이 강제. 큐 1번 거절·승인 후 다음으로 자동 진행.
